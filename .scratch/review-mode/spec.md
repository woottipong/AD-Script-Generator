# Review Mode: เปิดวิดีโอกับ SRT ที่มีอยู่แล้วมาตรวจแก้

Status: ready-for-agent

ใช้คำตาม [GLOSSARY.md](../../GLOSSARY.md) (Generate Mode, Review Mode, Job, AD Spot, Speech Segment) และการตัดสินใจเรื่องโครงสร้าง Job ใน [ADR-0002](../../docs/adr/0002-job-mode-and-video-source.md)

## เป้าหมายและเหตุผล

ผู้เขียนบทมีวิดีโอกับไฟล์ SRT บทบรรยายที่ทำไว้แล้ว และต้องการตรวจแก้บทเทียบกับวิดีโอด้วยหน้าทำงาน (workspace) เดิม คือไทม์ไลน์ ช่วงเสียงพูด คลื่นเสียง editor และการบันทึกอัตโนมัติ แล้วส่งออกเป็น SRT เหมือนฟีเจอร์เดิม วิดีโอจริงมักเป็น 1080p และอยู่บนลิงก์ในคลัง จึงต้องเปิดได้โดยไม่ต้องดาวน์โหลดเก็บและไม่เปลืองพื้นที่ทั้งบนเครื่องและบน server

## Goals

- หน้าแรกให้เลือกโหมด: "สร้างบทบรรยาย" (Generate Mode ที่มีอยู่) หรือ "แก้ไข SRT ที่มีอยู่" (Review Mode)
- Review Mode รับวิดีโอ `.mp4` จาก URL หรือจากไฟล์บนเครื่อง และรับไฟล์ `.srt` จากเครื่อง แล้วกด "ประมวลผล"
- การประมวลผลตรวจวิดีโอ สแกนเสียงหา Speech Segment และ Waveform Envelope อ่าน SRT เป็น AD Spot แล้วเปิด workspace เดิม
- แก้ข้อความและเวลาได้ เห็นบรรทัดที่ทับเสียงพูด บันทึกอัตโนมัติบน server และส่งออก SRT ได้เหมือนเดิม
- Job บันทึก `mode` และที่มาของวิดีโอ เพื่อย้ายเข้าฐานข้อมูลและผูกกับผู้ใช้ที่ล็อกอินได้ในอนาคต

## Non-goals

- ไม่เรียก Gemini ใน Review Mode และซ่อนทุกส่วนที่เกี่ยวกับการสร้างบท
- ไม่สลับโหมดกลางงาน งานหนึ่งอยู่โหมดเดียวตลอด
- ไม่มีรายงานเปรียบเทียบก่อนกับหลังการแก้ ใช้ตัวกรองที่มีอยู่
- ไม่ทำระบบผู้ใช้หรือล็อกอิน และยังไม่ใส่ `owner_id`
- ไม่มีปุ่ม "เปิดงานนี้" สำหรับงานเก่าที่ไม่ได้ active (ทำเป็นฟีเจอร์แยกทีหลัง)
- ไม่ดึงเฉพาะส่วนเสียงจาก MP4 ทาง URL (ทำทีหลังถ้าปริมาณเน็ตเป็นปัญหาจริง)
- ไม่ให้ server ของเราดึงวิดีโอจาก URL แทนเบราว์เซอร์

## Anti-goals

- ห้ามคัดลอกวิดีโอของ Review Mode ไปเก็บใน `.data/jobs` และห้ามให้เบราว์เซอร์ cache ไฟล์ทั้งก้อนลงดิสก์
- ห้ามแก้หรือตัดบรรทัดของ SRT ต้นฉบับเองตอนนำเข้า ยกเว้นบรรทัดที่เริ่มเลยความยาววิดีโอ
- ห้ามทำให้ Generate Mode เปลี่ยนพฤติกรรม

## การตัดสินใจที่ตกลงกันแล้ว

| เรื่อง | การตัดสินใจ |
|---|---|
| ที่มาของวิดีโอ | URL ที่ลงท้าย `.mp4` หรือไฟล์ `.mp4` บนเครื่อง ไม่ส่งวิดีโอขึ้น server ในโหมดนี้ |
| ข้อกำหนดวิดีโอ | ไม่ตรวจความละเอียดหรือ codec ภาพ ไม่จำกัดขนาดไฟล์ ความยาวไม่เกิน 60 นาที ต้องมีแทร็กเสียง AAC เพื่อสแกนเสียง |
| ไฟล์ SRT | UTF-8 (มีหรือไม่มี BOM) ถ้าถอดเป็น UTF-8 ไม่ได้ให้ลอง Windows-874 ข้อความหลายบรรทัดในหนึ่ง cue ให้คงไว้ ตัดแท็ก `<i>`, `<b>`, `<u>`, `<font>` ออก |
| บรรทัดที่ไม่ตรงวิดีโอ | นำเข้าตามจริงแล้วเตือน: ทับเสียงพูด, ทับบรรทัดข้างเคียง, สั้นกว่า 500 ms ส่วนบรรทัดที่เริ่มเลยความยาววิดีโอไม่นำเข้า และแสดงรายการให้เห็น |
| ทับเสียงพูด | เตือนและไฮไลต์ ไม่บังคับแก้ บันทึกและส่งออกได้ |
| ขยับเวลา | อิสระภายในความยาววิดีโอ ยาวอย่างน้อย 500 ms และไม่ทับบรรทัดข้างเคียง ใช้กับบรรทัดที่ผู้ใช้แก้ ไม่ล็อกในช่วงว่าง |
| บันทึก | บันทึกงานบน server แบบไม่มีวิดีโอ สถานะการบันทึกตามการตอบรับของ server เหมือนเดิม |
| เปิดงานเดิม | รุ่นแรกกลับมาทำต่อได้ผ่านการรีเฟรชหน้า ซึ่งเปิดงานที่ active อยู่ เหมือน Generate Mode ถ้าที่มาเป็น URL เล่นต่อได้ทันที ถ้าเป็นไฟล์บนเครื่องให้ผู้ใช้เลือกไฟล์เดิมอีกครั้ง และตรวจว่าชื่อกับขนาดตรงกัน |
| ปริมาณเน็ตตอนสแกน URL | รุ่นแรกดึงทั้งไฟล์ผ่านเน็ตหนึ่งครั้ง (รวมภาพ) โดยไม่เก็บลงดิสก์ |
| ส่งออก | ปุ่ม "ส่งออก SRT" เดิม ใช้ `generateSrtContent` เดิม บรรทัดที่ผู้ใช้ตั้งเป็น "ข้าม" จะไม่อยู่ในไฟล์ที่ส่งออก |
| URL เปิดไม่ได้ | แจ้งว่า "ลิงก์นี้เปิดจากเบราว์เซอร์ไม่ได้ กรุณาดาวน์โหลดแล้วเลือกเป็นไฟล์แทน" |
| ชื่อเรียก | ทั้งสองโหมดยังเรียกแต่ละบรรทัดว่า AD Spot ใน Review Mode AD Spot ทับ Speech Segment ได้แต่ต้องถูกเตือน |

## โครงสร้าง Job (schema version 2)

```ts
type JobMode = 'generate' | 'review';

type VideoSource =
  | { kind: 'server_copy'; local_file_path: string }
  | { kind: 'url'; url: string }
  | { kind: 'local_file'; file_name: string; file_size: number };

interface PersistedJobState {
  schema_version: 2;
  job_id: string;
  mode: JobMode;
  video_source: VideoSource;
  srt_source?: { file_name: string; cue_count: number; imported_at: string }; // Review Mode เท่านั้น
  // field อื่นเหมือนเดิม: status, video_metadata, vad_config, vad_output, spots, batches, created_at, updated_at, ...
}
```

- `local_file_path` ที่อยู่ชั้นบนสุดย้ายเข้า `video_source` ทุกที่ที่อ่านค่านี้ (ไฟล์สำหรับ Gemini, `GET /api/jobs/:jobId/video`) ต้องอ่านจาก `video_source` แทน
- งานที่ไม่มี `schema_version` ให้ Job store แปลงตอนอ่านเป็น `mode: 'generate'` และ `video_source: { kind: 'server_copy', local_file_path }` แล้วบันทึกเป็นรูปแบบใหม่ในครั้งถัดไปที่บันทึกงานนั้น ตัวแปลงอยู่ใน `src/utils/jobStore.ts` ที่เดียว
- งาน Review Mode มี `batches: []` และสถานะเป็น `READY` ตั้งแต่ server สร้างงาน
- AD Spot ที่มาจาก SRT: `decision: 'generate'`, `text` คือข้อความของ cue, `original_start_ms`/`original_end_ms` เท่ากับเวลาของ cue ตอนนำเข้า
- `video_metadata.height` เก็บความสูงจริงของวิดีโอ ส่วนการตรวจ 480p ใช้กับ Generate Mode เท่านั้น
- `GET /api/jobs` และหน้าจัดการพื้นที่จัดเก็บแสดงงาน Review Mode ได้ ขนาดที่แสดงคือขนาดของโฟลเดอร์งาน ซึ่งไม่มีวิดีโออยู่ในนั้น

## ขั้นตอนของผู้ใช้

1. หน้าแรกแสดงสองการ์ดให้เลือกโหมด ปุ่ม "เริ่มงานใหม่" พากลับมาที่หน้านี้
2. Review Mode แสดงช่องวาง URL หรือปุ่มเลือกไฟล์วิดีโอ และปุ่มเลือกไฟล์ SRT ปุ่ม "ประมวลผล" กดได้เมื่อมีทั้งวิดีโอและ SRT
3. กดประมวลผลแล้ว:
   - ตรวจวิดีโอตามข้อกำหนดของ Review Mode
   - อ่าน SRT ถ้าอ่านไม่ได้หรือไม่มี cue เลย ให้หยุดพร้อมข้อความที่บอกเหตุผล
   - สแกนเสียงด้วย worker เดิม และแสดงความคืบหน้าด้วย feedback เดิม
   - สร้าง Job ของ Review Mode บน server แล้วเปิด workspace
4. workspace ใช้ส่วนประกอบเดิม ยกเว้นส่วนที่ต้องซ่อน: ปุ่มและสถานะการสร้างบท, คิวของ batch, ปุ่มทำต่อหรือลองใหม่, และเมนูสแกนใหม่ถ้าต้องผูกกับการสร้างบท
5. แสดงจำนวนบรรทัดที่มีคำเตือน (ทับเสียงพูด, ทับบรรทัดข้างเคียง, สั้นเกิน) และกรองดูเฉพาะบรรทัดเหล่านั้นได้
6. แก้ข้อความหรือเวลาแล้วระบบบันทึกอัตโนมัติ ส่งออก SRT ได้ตลอดเวลา

## การเล่นวิดีโอและการสแกนเสียง (ไม่เปลืองพื้นที่)

- **การเล่น:** ใช้ URL เป็น `src` ของ `<video>` ตรงๆ หรือใช้ blob URL ของไฟล์บนเครื่อง ทดสอบกับไฟล์ตัวอย่างแล้ว (1920×1080, 24:43, 71 MB) โหลดข้อมูลวิดีโอใช้ 0.24 วินาที และ seek ใช้ 0.06–0.25 วินาที
- **การตรวจวิดีโอและการสแกนเสียง:** `videoValidator.ts` กับ `vad.worker.ts` อ่านไฟล์เป็นก้อนด้วย `file.slice()` อยู่แล้ว ให้เพิ่มทางอ่านข้อมูลเป็นช่วง โดยมีสองแบบที่ใช้แทนกันได้ คือ `File` และ URL ที่ดึงด้วย HTTP Range
  - ใช้ `fetch` กับ `cache: 'no-store'`
  - ดึงทีละก้อนแล้วทิ้ง ไม่ถือทั้งไฟล์ไว้ในหน่วยความจำ
- **ขนาดไฟล์และการดึงจาก URL:** อ่านขนาดไฟล์จาก `Content-Length` ของคำขอ `HEAD` เพราะ `Content-Range` ไม่ได้ถูกเปิดให้อ่านข้าม origin ทดสอบกับ URL ตัวอย่างแล้ว ได้ผลดังนี้
  - `HEAD` ได้ 200 พร้อมขนาด 71,225,137 ไบต์
  - `fetch` ที่ใส่ `Range` ได้ 206 และได้จำนวนไบต์ตรงตามที่ขอ
  - host ส่ง `Access-Control-Allow-Origin: *` และ URL ไม่มี token
- **URL ที่ใช้ไม่ได้:** ถ้า URL ไม่รองรับ CORS หรือ Range ให้แสดงข้อความตามตารางด้านบน
- **การเก็บ URL:** เก็บ URL ตามที่ผู้ใช้วาง (การตัดสินใจของผู้ออกแบบ) ถ้าวันหน้าต้องรองรับลิงก์ที่มี token หมดอายุ ค่อยออกแบบเพิ่ม
- **ผลที่เก็บ:** เก็บแค่ผลสแกน (`vad_output` ซึ่งรวม `waveform`) ลงใน Job ครั้งหน้าที่เปิดงานจึงไม่ต้องสแกนซ้ำ

## กฎเวลาและการตรวจที่ server

- `src/utils/spotTiming.ts` ยังเป็นที่เดียวของกฎเวลา ให้เพิ่มกฎของ Review Mode ไว้ที่นี่:
  - อยู่ในความยาววิดีโอ
  - ยาวอย่างน้อย `MIN_SPOT_DURATION_MS`
  - ไม่ทับบรรทัดข้างเคียง
  - การทับ Speech Segment เป็นคำเตือน ไม่ใช่ error
- การลากใน timeline และปุ่ม nudge ใน Review Mode ใช้ขอบเขตเป็นความยาววิดีโอและบรรทัดข้างเคียง ไม่ใช้ช่วงว่าง
- `PATCH /api/jobs/:jobId/spots` ตรวจตาม `job.mode`:
  - **Generate Mode:** ใช้กฎเดิม
  - **Review Mode:** ตรวจกฎเวลาเฉพาะบรรทัดที่ `start_ms` หรือ `end_ms` ต่างจากที่บันทึกล่าสุด การแก้ข้อความหรือ decision อย่างเดียวไม่ต้องตรวจกฎเวลา บรรทัดจาก SRT เดิมที่ผิดกฎจึงยังบันทึกได้ บรรทัดที่เวลาเปลี่ยนต้องผ่านกฎ Review Mode ทุกข้อ ณ ตำแหน่งใหม่ (การตัดสินใจของผู้ออกแบบ)
- **บรรทัดข้างเคียงตามกฎ "ไม่ทับบรรทัดข้างเคียง":** นับเฉพาะบรรทัดที่ decision ไม่ใช่ "ข้าม" เพราะบรรทัดที่ข้ามไม่อยู่ในไฟล์ที่ส่งออก คำเตือนเรื่องทับกันก็นับแบบเดียวกัน (การตัดสินใจของผู้ออกแบบ)
- **บรรทัดที่ทับข้างเคียงอยู่ตั้งแต่ตอนนำเข้า:** ถ้าผู้ใช้ลากหรือ nudge บรรทัดนี้ clamp จะดันขอบให้ออกจากการทับ ไม่ต้องรองรับการขยับที่ยังทับอยู่ (การตัดสินใจของผู้ออกแบบ)
- route ที่ใช้ Gemini (`start`, `analyze-batch`) ตอบ HTTP 409 เมื่อ `job.mode === 'review'`
- **ระหว่างที่งาน Generate Mode กำลังวิเคราะห์:** การสร้างงาน Review Mode ตอบ HTTP 409 เหมือน `jobs/init` เพราะการสร้างงานจะย้าย active pointer และทำให้งานที่กำลังวิเคราะห์หายไปจากหน้าจอ (การตัดสินใจของผู้ออกแบบ)
- **การตรวจตอนสร้างงาน Review Mode:** ใช้โครงสร้าง validation แบบเดียวกับ `jobs/init` แต่ใช้ขีดจำกัดของ Review Mode
  - ไม่ตรวจความสูง 480 และ codec ภาพ
  - ไม่จำกัดขนาดไฟล์
  - ความยาวไม่เกิน 3,600,000 ms
  - เพดาน `waveform.peaksBase64` ต้องพอสำหรับ 60 นาที (20 ms ต่อช่อง ประมาณ 240,000 ตัวอักษร) จึงปรับเพดานเป็น 250,000 ตัวอักษรทั้งสองโหมด ไม่ขัดกับ ADR-0001 ซึ่งตัดสินแค่รูปแบบการเก็บ ไม่ได้กำหนดเพดาน (การตัดสินใจของผู้ออกแบบ)

## การตรวจสอบ

- **Unit test:**
  - parser ของ SRT: UTF-8, BOM, Windows-874, หลายบรรทัด, แท็ก, cue ที่เลยความยาววิดีโอ
  - กฎเวลาของ Review Mode
  - การแปลงงานเก่าเป็น schema version 2
  - การตรวจ PATCH ตามโหมด
- **Integration test:** สร้างงาน Review Mode ผ่าน HTTP, PATCH ทั้งบรรทัดที่ไม่เปลี่ยนและที่เปลี่ยน, และยืนยันว่า `start` ตอบ 409
- **Browser test:** เพิ่มสคริปต์ใน `tests/browser/` ที่จำลอง API ครอบคลุมการเลือกโหมด, การซ่อนส่วนสร้างบท และการแสดงคำเตือน
